# R3 — Cross-Module Reference Integrity Review

**Scope:** 14 platform-grounded primesoft-hrms BRDs (`docs/brd/v3/PS01..PS14*.md`).
**Concern:** one cross-cutting axis only — when module A says it consumes/feeds module B, does the referenced entity/event/FR actually exist in B and agree on direction and semantics?
**Date:** 2026-07-01 · **Reviewer:** integration-reviewer (report-only, no edits to BRDs).

---

## Verdict

The suite is **unusually well cross-referenced**: every module uses the canonical `PS01..PS14` code scheme, carries an explicit "Alignment with PrimeSoft Platform", integration-contract, and dependency section, and the *large structural* contracts reconcile cleanly on both sides — the PS11→PS12 service-verification gate (PS12 FR-08/FR-13 ↔ PS11 FR-18), the PS09 penalty→PS06/PS10/PS11/PS12 downstream map, the PS10-owns-increments / PS06-mirrors agreement, the PS13 polymorphic `:attach`/`:fetch` contract, and the PS14 read-only mart model are all reciprocated. **The weak seam is the PS12 SR write-path:** several upstream producers (PS05, PS06, PS04, PS02, PS01) emit SR `event_type` strings or use a `source_module` identity that does **not** match PS12's published taxonomy / per-source allowlist (Appendix B/C, FR-02 BR-02.1) — yielding dangling event types and one genuine ownership conflict (identity-change events claimed by both PS01 and PS02). Separately, the flagship **PS03→PS04 leave handoff disagrees on the correlation key** (`application_id` vs `leave_spell_lineage_id`) and on the signed-capture shape, two analytics feeds (PS02/PS04→PS14) are not reciprocated by PS14's source list, and one promotion-eligibility handoff (PS07→PS06) is advertised by PS07 but not consumed by PS06. No module is internally broken; the fix is a normalization pass centred on PS12's taxonomy and the PS03/PS04 join key.

**Counts by severity:** High **4** · Medium **6** · Low **2** · Total **12**.

## What reconciled correctly (no finding)

- **PS11 ↔ PS12 verification gate** — PS12 FR-08/FR-13 provides the signed-off/locked SR verification + single pull-feed; PS11 FR-18 blocks all benefit calculation until `service_verifications.status = SIGNED_OFF/LOCKED`. Bidirectional, names match.
- **PS09 → PS06/PS10/PS11/PS12 penalty effects** — PS09's penalty→downstream map (sealed-cover/promotion freeze→PS06, subsistence/recovery→PS10, pension cut/Rule-9→PS11, SR events→PS12) is reciprocated by each consumer's boundary section.
- **PS10 owns increments / PS06 mirrors** — both sides agree PS10 is system-of-record for increments and stepping-up; PS06's `increment_monitor` is explicitly a mirror/monitoring view.
- **PS13 attach contract** — `documents:attach` / `:fetch?intent=` polymorphic link `(module_code, entity_name, entity_ref_id, link_role)` is consumed consistently by PS01–PS12; lifecycle inbox (`EMPLOYEE_RETIRE/MERGE` from PS01, `CASE_CLOSE` from PS09, retire-confirm from PS11) reciprocated.
- **PS14 read-only marts** — PS14 never writes source data / SR; reads via versioned `source_data_contract` + Debezium CDC; PS12 SR read-only, PS13 export-refs-only — all consistent with each owner's "PS14 reads, never writes" statement (except the PS02/PS04 omission in F9).
- **PS05 → PS01 / PS10 handoffs** — `POSTING_UPDATE`/org-placement to PS01 and `PAY_CONTINUITY`/`LPC_REQUEST` to PS10 are reciprocated by PS01 (org owner) and PS10 (pay executor).

## Method & confidence

Each module's Alignment, API/Integration, and Traceability/Dependency sections were extracted and the producer-side `event_type`/entity/API identifiers were cross-checked against the consumer-side catalog/allowlist (notably PS12 §16.2/§16.3 and FR-02). High/Medium findings were verified against the literal strings in the source files (line numbers cited). Note that PS12's launch catalog is marked "illustrative" and its taxonomy is versioned/extensible — so the event-name findings (F1, F4, F5, F10) are resolvable by taxonomy entries + allowlist edits rather than redesign, but they are real at the current specification level because PS12 FR-02 BR-02.1 enforces `source_module ∈ allowed_source_modules` and type existence at ingestion.
