# R1 — Digital Service Register (PS12) Ingestion-Contract Consistency Review

**Scope:** One cross-cutting concern — does every module that writes to the PS12 Digital Service Register (SR) ledger call the *same* governed ingestion contract, with event types, idempotency/dedup keys, reversal semantics, provenance, ledger-entity naming, and tenant scoping that are mutually consistent?

**Owner reviewed:** `docs/brd/v3/PS12-digital-service-register.md`
**Writers reviewed:** PS04, PS05, PS06, PS08, PS09, PS10, PS11
**Grounding:** `docs/brd/PLATFORM_FOUNDATION.md`, `docs/brd/MODULE_RECONCILIATION.md`
**Date:** 2026-07-01 · **Reviewer:** integration-reviewer (evidence-first, report-only)

---

## Verdict — **MATERIAL CONFLICTS**

PS12 *does* define a single, explicit, well-engineered write-port (`POST /api/v1/sr/ingest`, the "only write path", with syntactic `(source_module, source_reference_id, source_event_version)` + semantic `fact_key` dedup, a reversal envelope, a `source_module` provenance allowlist, a versioned `sr_event_type` taxonomy, and a `tenant_id`-scoped per-employee hash chain). The **ledger entity name (`service_register_events`) and its net-new-on-P05 character are consistent across all eight files** — that part is clean, and **PS09 is a reference-quality writer that matches the owner contract end-to-end** (endpoint, syntactic tuple, `fact_key`, `source_module=PS09`, `is_reversal`/`reverses_source_reference_id`, `*_REVERSAL` taxonomy, supersede-not-delete).

But the **integration contract does not actually line up**: (1) the write-port **URL differs** — PS12 says `/api/v1/sr/ingest`, while PS04 and PS05 both call `/api/v1/sr/events`; (2) the **idempotency/dedup key is reinvented per writer** and the canonical syntactic-tuple fields are not populated by anyone except PS09; (3) `fact_key` — which PS12 makes **mandatory for qualifying-service-bearing events** (`SR_FACT_KEY_REQUIRED`) — is absent from PS04/PS05/PS06/PS10, the very modules whose events count toward pension; (4) PS05 invents a `COMPENSATING` reversal event type that is not in PS12's taxonomy; and (5) the **writer set and PS11's write/read role are stated four different ways** across PS12 and the reconciliation doc. These are wiring-level mismatches that would fail at first integration and partially defeat the anti-double-counting guarantee. Hence **MATERIAL CONFLICTS**, not minor drift.

## What is already consistent (no action)

- **Ledger entity name & character:** all eight files name the ledger `service_register_events`, attribute ownership to PS12, and describe it as net-new on the P05 audit/immutability substrate (DB-trigger, immutable, ≥7-yr) — **consistent** (F-14 is only a wording nit). (PS12 L392; PS04 L310; PS05 L294/L711; PS06 L279; PS08 L223/L232; PS09 L264; PS11 L189.)
- **Append-only / supersede-not-delete:** no writer hard-deletes; corrections are new rows. The *mechanism names* drift (F-04), but the no-hard-delete invariant holds everywhere. (PS12 rule 9 L793; PS05 L764; PS06 L994/L2082; PS08 L1493; PS09 L793.)
- **PS09 is the reference implementation:** matches the owner contract on endpoint intent, syntactic tuple, `fact_key`, `source_module`, reversal envelope, and supersession — use it as the template to bring the other writers into line.

---

## Recommended remediation order

1. **F-01 + F-06 (one amendment):** freeze the canonical write-port URL and the canonical writer matrix in PS12 FR-01/FR-02; mirror in Reconciliation §D.
2. **F-02 + F-03:** make `fact_key` and the `(source_module, source_reference_id, source_event_version)` tuple required on every writer's ingest call (acceptance-tested).
3. **F-05:** resolve PS11 writer/consumer and name the owner of the separation/superannuation event.
4. **F-04 + F-07 + F-08:** publish the missing `sr_event_type` codes (incl. an appraisal mapping) and replace `COMPENSATING`/`AMENDMENT` with the PS12 reversal envelope.
5. **F-09–F-14:** payload-field and wording fixes (provenance, tenant scoping, direct-write framing, 503 residue, platform-primitive nit).
