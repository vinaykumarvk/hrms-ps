0. About this document
References BRD Base 6 (whole); Prototype v20_1_2_1 (leave screens); functional-spec-author non-repetition protocol.
This Functional Specification adds the build layer for Leave Management: screen specifications, complete API contracts, validation, per-screen RBAC projection, interaction states, and the operational layer (scheduled jobs, message catalogue, menu entitlement, dashboard widgets). It does not restate anything the BRD already fixes. Every business rule, data field, permission-matrix cell, NFR target, state transition and glossary term lives in the BRD and is referenced here by section number.
The single-source-of-truth contract Already in the BRD (a business rule, data-field definition, locked decision, NFR, permission, state transition) → referenced here as “BRD §X”, never copied. New build-layer detail (screen layout, field control + behaviour, request/response/error schema, validation format, per-screen role projection, UI states, micro-copy) → authored here. This is the FS’s job. A conflict (prototype contradicts the BRD) or a gap (neither covers it) → surfaced in §8 with the agreed resolution and where it was actioned (BRD / FS / prototype); never silently decided in the body.

Document architecture. The full programme architecture is a Foundation FS (shared validation, API conventions, global UI states, scheduled jobs, message catalogue, menu map) plus one FS per module. No Foundation FS exists in the project yet, so the leave-relevant slices of those cross-cutting sections are authored here (§5, §7) and explicitly marked as belonging in the Foundation FS when it is created; module teams must not duplicate them.
Leave-type vocabulary. The canonical leave-type catalogue is BRD §4.5.1 (SL, PL, PL_CC, WWC, WL, PATL, ML, ADL, MCL, SPL, SBL, OH_*_26, Unpaid/LOP). The prototype’s sample data used alternative codes (CL, EL, LWP, BL, SAB, COMP, PAT); the prototype has been re-skinned to the canonical codes and this FS uses the BRD codes throughout (§8 OPEN-02).

2. Screen Specifications
One subsection per prototype leave screen. Each opens with its prototype id and references, then layout regions, a field table (new content is the Control and On-screen behaviour columns; the other columns are references), interaction states, and an actions table that points at the API contract in §4 and message ids in §7.2.
Global UI state standard. Unless a screen overrides it below, every screen follows the standard loading (skeleton rows / spinner), error (inline banner with retry, message id from §7.2), and no-permission (screen not in menu per §6; deep-link returns 403 with FORBIDDEN copy) patterns. These belong in the Foundation FS once created.

Prototype screen id apply-leave
References FR-M04-001 (form), FR-M04-009 (sandwich), FR-M04-010 (decision matrix), FR-M04-013 (combined), FR-M04-017 (hourly); entity leave_applications §4.5.4; POST /leave-applications §4 (4.1); state §8.2; D04, D09, D10, D19, D29.

Approval-flow preview (read-only): resolved Stage-1 approver; Stage-2 pool note for two-stage types.
Footer actions: Save draft, Submit application.

7.1 Scheduled jobs & background processing (leave)
References Rules: BRD §5.5 (FR-M04-002 cycle, -009 sandwich, -016 smart suggestions), §8.2 (escalation), leave_platform_settings Cluster 8 (cron flags §4.5.7), background jobs entity §4.14.8. Cadence/idempotency/failure authored here; rules referenced.
Job id
	Trigger / cadence
	Reads / writes
	Logic (rule ref) · idempotency · failure

JOB-M04-ESCALATE
	Hourly scan
	leave_applications
	Sets ESCALATED + escalation_fired_at after 10 days inaction (FR-M04-003/§8.2). Idempotent on escalation_fired_at null-check. Failure: retry next run; emits LEAVE_ESCALATED.

JOB-M04-ACCRUAL
	Per accrual_frequency (quarterly/monthly) at 00:00 IST
	leave_policies → employee_leave_balances
	Credits accrual per policy (§4.5.2/§4.5.1). Idempotent per (employee,type,period) key. Failure: per-employee retry; partial-failure isolated.

JOB-M04-CARRYFWD
	Year-end (leave cycle boundary)
	employee_leave_balances
	Computes carry_forward_to_next_year within carry_forward_cap_days (§4.5.1/§4.5.3). Idempotent per (employee,type,year). Locks balance rows during run.

JOB-M04-LOP
	25th of month (cutoff, calendar-based)
	leave_applications → LOP feed (M06 Phase 2)
	Emits LOP records for 26th–25th window (FR-M04-002). Runs even if 25th is weekend/holiday. Idempotent per (employee,cycle).

JOB-M04-SANDWICH
	Month-end window (sandwich_auto_cron_from/till)
	leave_applications, holiday/weekly-off
	Re-evaluates approved leave for sandwich debit when enabled (FR-M04-009). Gated by apply_sandwich_leave. Idempotent re-compute; audit-logged.

JOB-M04-SMART
	Daily at configured time
	employee_leave_balances, comp-off
	Generates CF/comp-off expiry suggestions (FR-M04-016). Fires once per balance per lead-time threshold (no daily spam). Honours notification prefs.

JOB-M04-AUTOREJECT
	Configured date each month (gated)
	leave_applications
	Auto-rejects pending per reject_pending_via_date_cron (Cluster 8). Auto-APPROVE remains disabled platform-wide (D06). Idempotent per cycle.

JOB-M04-DECISION-REEVAL
	On employment-history change (event)
	leave_policies.decision_matrix_config
	Re-evaluates matrix outcome for affected employees (FR-M04-010); invalidates cached cycle result.

Build layer over BRD Base 6 · confidential · Page of # Prototype Sync Addendum — Batch 2: Employee-role Leave review (June 2026)
Reflects the Batch-2 Employee-role Leave review against the clickable prototype (v2). Complements — does not replace — the body of this FS.
Config-driven application lists
The leave-application screen draws its reason list from the Leave Reasons master (assignment / group-company scoped) and its leave-type list from the active leave policies — neither is hardcoded. Reason is mandatory (Leave settings) and an attachment is required beyond the policy-defined day threshold; both are enforced at submit.
Employee leave revocation
An employee may request revocation of an approved leave application, including past-dated approved leave, which routes to the approval flow and refunds the balance on approval. System-deducted leave is not employee-revocable (Leave settings). The employee-side “Revoke” action opens a revocation request — it is not a silent action.
Optional holidays & holiday calendar
The holiday calendar distinguishes Mandatory / Optional / National holidays and is scoped to the employee’s location / assignment (holiday master Assigned-location / Work-area). Employees can apply for optional holidays and request flexible-holiday date changes where enabled.
Leave encashment — not employee self-service (Phase 1 decision)
Leave encashment is not an employee self-service action in Phase 1. HR Admin is both the initiator and the decision maker: HR Admin initiates and authorises encashment, either case-by-case during employment (HR Ops) or as part of full-and-final on exit (E7 clearance computes the encashable balance and passes it to FnF). Encashment is config-gated (encashment window; “encashable on exit” per policy) and may be delegated via the encashment-authorisation capability. The employee sees only the resulting balance / history entry — there is no employee-facing apply screen.
Comp-off — in scope for employees (Phase 1 decision)
Comp-off is in scope for employees. Two employee-facing paths exist: (1) availing — the employee applies for comp-off as a selectable leave type on the leave-application screen, subject to the comp-off policy (half-day, past-dated, lapse, auto-approve); and (2) credit — the employee raises a comp-off credit request (earned via weekend / holiday / overtime working) from the attendance screen. Both route to the comp-off approval queue; credit, lapse and clubbing are governed by the tenant comp-off / overtime policy.
Manager leave approval — reject & direct revoke
When a manager rejects a leave request a rejection reason is mandatory (config: Make Rejection Reason Mandatory For Leave Requests = Yes). A manager may also directly revoke an approved leave — including past-dated and system-deducted leave (config: Allow Managers/Approvers To Revoke … Past-Dated / System-Deducted Approved Leave = Yes; the “otherwise only admins” restriction is off) — with a mandatory reason, after which the employee is notified. Revoke is surfaced on every approved row of the reportee’s leave history.
PL encashment — HR Admin decision only
PL encashment is an HR Admin decision (Approve / Reject), taken case-by-case during employment and at FnF. It is not an employee self-service action and is not raised as a separately-initiated request — the encashment screen is the HR Admin decision queue. Leave Admin does not have access to PL encashment (it is an HR Admin authoritative action).
Manager-role review (Round 3 follow-up B)
Reportee leave actions consolidated. The manager's reportee Leave surface and the per-member Leave history now carry a consistent action set: apply leave on behalf, revoke approved leave (reason + audit), request balance adjustment (to Leave Admin), and a link to the full leave history. Resolves the earlier divergence between the two leave surfaces.
