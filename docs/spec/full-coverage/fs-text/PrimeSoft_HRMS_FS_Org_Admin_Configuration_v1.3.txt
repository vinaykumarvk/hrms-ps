2. Workflow Builder — cfg-workflows
Writes the Platform W.1 workflow model; executed by P01. Grounded in Workflows (68) + Workflow Stages (189; action types data-collection-form 99 / notification 67 / document-generation 23) + Flow Category (3). List of workflows (filter by module/category/status) + Add. Builder: workflow code, flow category, pattern (Series / Parallel-All / Parallel-Any / Conditional / Dynamic-approver, per Appendix D), then ordered stages — each stage: name, action type (data-collection form → select a W.2 form; notification → select W.3 config; document-generation → select M11 template), assignee resolution, allotted time, skip setting (§4), SLA (§4), visibility & confidential roles, send-back routing, button aliases, per-event email recipients. Validation: ≥1 stage, every stage has assignee resolution, no circular stage reference (VAL-FLOW-NOCYCLE), referenced form/template/notif exist. Versioning: save validates; activation immediate for new instances; in-flight instances pinned to their version; deprecate-not-delete while instances are active (P01).
3. Approval-Flow Builder — cfg-approval-flows (new — resolves prior gap)
Writes the Platform W.1 approval-flow model; executed by P01. Grounded in Approval Flow (76) + Approval Flow Stages (104). Approval flows are built separately from workflows because their stage shape differs (approver context + decision matrix vs action-type stages). Builder: flow code, module transaction, ordered approval stages — each: stage name, approvers (named role / reporting-chain position incl. L1-with-fallback / named individual / cost-centre head), approver job-level/grade constraints, action, allotted time, decision matrix (§4), re-route, exception/escalation stage (e.g., offer-letter joint authority; OT exceptional-by-hours), send-back, visibility/confidential roles, button aliases, per-event email recipients. Validation: ≥1 stage, every approver resolvable, exception thresholds valid. Versioning identical to §2. Builder shares the cfg-workflows shell if the design prefers one entry point — see §13.
4. Skip Settings, SLA Timers & Decision Matrices
Writes W.1 sub-models; consumed by §2/§3 and by P01 at stage entry. - Skip Settings — cfg-skip (Skip Setting 4 + Stages 6): skip-condition subject/rule, reassign-to-role; resolved at stage entry. - SLA Timers — cfg-sla (SLA Setting + Stages): SLA level, trigger before/after, duration, breach output (delegate / auto-act), delegate-to-roles, cancel-dependent-stages; on breach → escalation event + notification (X.2) + audit. - Decision Matrices — cfg-decisionmatrix: rule table mapping context → routing/decision; referenced by leave routing and approval stages. Validation: VAL-REQUIRED/ENUM; matrix completeness.
5. Form Builder — cfg-forms (new — resolves prior gap)
Writes the Platform W.2 form model; assembles fields defined in the Org Admin Master Data FS cfg-custom (40 fields). Builder: form code, target context (onboarding cluster / workflow data-collection stage / leave or attendance request / interview guide / separation / exit-interview / custom application form), field set (add fields from the custom-field library + standard fields), conditional logic (show/required-if), per-role field visibility (reference RBAC §3.9), data-binding + write-back to the entity, translations/i18n, and versioning (a form used by in-flight instances keeps its version). Validation rules attach via Foundation VAL-* ids (never re-authored). Validation: at least one field; bound fields reference an active custom-field/standard field; conditional references resolve.
6. Notification Configuration — cfg-notif
Writes the Platform W.3 notification-config model; delivered by X.2; copy lives in the Foundation §5 / module-FS message catalogue (referenced by id). Builder: per event / stage recipient resolution (default recipients / additional recipients / CC roles / CC users), channel selection (IN_APP / EMAIL / SMS per §9.1), reminder cadence vs escalation distinction + escalation targets, role→user expansion, suppression/dedup, digest mode, per-tenant sender config, and template selection by Msg id. Honors §9.9: EMAIL mandatory for approval/statutory events (not suppressible); 5-attempt retry + DLQ (X.2). The builder configures who/which-channel/when; it does not author message copy.
7. RBAC Administration & Entitlement Grants
Edits the RBAC model (RBAC Design Document v1.2); enforced by P02. The screens manage the model; they never define enforcement mechanics. - RBAC Roles & Permissions — cfg-rbac (grounded in Standard Permissions exports, 8 policies): view/edit the role taxonomy, the permission matrix (152 × 18) per role × module × action (enable/disable, the as-configured baseline per the Matrix↔Exports reconciliation), field-level access, and the capability-flag registry (4 flags: BGV review, Letter Admin, Asset Custodian, Dept-Head Audit Certify) + the two HOD configurable grants. Every change writes security_audit_log (P05). - Entitlement Grants — cfg-grants: grant/revoke individual entitlements (time-bound, mandatory expiry, audited). Validation: VAL-DATE (expiry mandatory), scope defined. - UAGs are shared with HR Admin and authored in the Org Admin Master Data FS (§2.11) — referenced here, not duplicated.
8. Tenant-wide Platform Settings
The tenant behaviour toggles consumed by the operational modules (the policies that bind them are in the HR Admin FS). - Leave Platform Settings — cfg-leave-platform (Leave Settings export, 131 toggles): revocation rules, escalation/SLA, sandwich/clubbing, rounding, balance-display, encashment window, optional-holiday behaviour, combined balance, blackout enablement, etc. - Attendance Platform Settings — cfg-att-platform (Attendance Settings export, 147 toggles): regularization restriction, auto-approve/reject, escalation, exclusions for present-day/late/early, infraction framework, geofencing enablement, overtime display, cycle/freeze, widget visibility, etc. - These are tenant-scope behaviour switches; they do not define policies (that is HR Admin). Changes audited (P05) and cascade per Platform §0.3.
9. Security & Access Configuration
SSO & Authentication — cfg-sso: SSO policy, session/expiry (Platform §0.2 / BRD §7.4).
Integration Credentials — cfg-integrations: encrypted credentials, rotation, per-integration scope (Platform X.3 / P04).
IP Whitelist — cfg-ip (12 networks), Biometric Devices & Locations — cfg-devices (FR-P04-002), Geofence enablement — cfg-geofence (fences mastered in Org Admin Master Data FS; toggled here). Validation: VAL-REQUIRED/ENUM; credential encryption never returns secrets to the client.

10. Per-Screen RBAC Projection & Menu
References RBAC v1.2 §2.1 (Org Admin), §2.1.1 (build vs bind), Foundation §6. All §2–§9 screens are Organisation Admin only (the tenant configuration owner; the only cross-entity role). HR Admin / module admins may view and bind the resulting definitions but cannot create/edit them. Platform Super Admin is not involved. RBAC administration (§7) and SSO/integration (§9) are the most sensitive — every change writes security_audit_log (P05). Menu surfaces under Foundation §6 “Settings / Configuration” (Documents & workflow, IAM & security, Tenant & entities, Leave & attendance settings groups).
11. Operational Layer
These builders produce configuration consumed by the P01 engine, X.2 notifications, and P02 enforcement — they register no new scheduled jobs. Every create/edit/activate/deprecate writes an audit row (P05); RBAC/SSO/integration changes write security_audit_log. No new message copy (copy lives in Foundation §5).
