0. How to read this specification
This Functional Specification is the build layer on top of the BRD. It specifies what the BRD deliberately leaves out — screen composition, field-level UI behaviour, complete API contracts, validation, per-screen role projection, interaction states, scheduled jobs, and the message catalogue — for the Onboarding module (M02). It does not repeat business rules, data-field definitions, the permission matrix, NFR targets, state-machine transitions, or glossary terms that the BRD already fixes; those are referenced by section number.
Each section opens with a References block identifying the BRD sections and prototype screens it builds on, so any fact is traceable to its single source. Where the prototype and BRD conflict, or where neither covers something the build needs, the item is not silently decided inside the spec body — it is recorded in §8 (Open Items, Conflicts & Recommendations) with a named owner and a proposed resolution marked PROPOSED — confirm before build.
Foundation FS dependency. PrimeSoft does not yet have a published Foundation FS. The cross-cutting build content this module relies on — the shared validation/regex catalogue (§5), the global UI-state standard, the API conventions, the role→menu entitlement map, the scheduled-jobs register, and the message catalogue (§7) — properly lives once in a Foundation FS. Until that document exists, the M02 slices of those registers are authored here and tracked as accepted follow-on OPEN-FS-M02-12 (§8). On Foundation FS publication, the entries in §5 and §7 marked “Foundation-owned” move there and are referenced from here.

Interaction contract
Auto-save: every 30s while focused with unsaved changes; writes onboarding_form_responses rows at field_status=DRAFT. Cadence governed by DO19 / FR-M02-002 — not restated. PUT /api/v1/onboarding/instances/{id}/form-responses (§4).
“Last saved at HH:MM:SS” indicator: required by FR-M02-002; added to v20.2 onboarding-form — M02-14 (§8).
Submit: validates server-side, transitions field_status DRAFT→SUBMITTED, advances instance FORM_IN_PROGRESS→DOCUMENTS_PENDING (§8.5). POST …/form/submit.
Rehire pre-fill (DO24): non-sensitive fields sync from M01; sensitive fields (per M01 §3.9 flag) require re-entry for consent freshness — eligibility derived automatically, no M02 list.
Variant switch: hides/shows the Previous-employer section and Middle-name mandatory flag per Appendix J population rules.
States
Partial-data: section progress chip “n of 12 complete”; resuming restores DRAFT values. Network failure during auto-save holds state client-side, retries on reconnect, then updates the saved-at indicator (FR-M02-002 edge case). Loading/empty/error/no-permission per Foundation standard.

POST /api/v1/onboarding/instances — initiate (drives §8.5 — → INITIATED)
Request:
{ source_mode: ‘COUNTERSIGNED’|‘CROSS_ENTITY’|‘AD_HOC’,
candidate_id?: uuid, // required unless AD_HOC
employee_id?: uuid, // CROSS_ENTITY rehire/transfer
process_id: uuid, // FK onboarding_processes §4.7.1
target_date_of_joining: date, // VAL-DATE-FUTURE
joining_location_id: uuid,

welcome_page_template_id?: uuid, portal_access_timing: enum,

optional_document_ids?: uuid[] }
Response 201: { id, state:‘INITIATED’, initiated_by_user_id, target_date_of_joining,
cluster_summary, bgv_case_id, portal_access_at }
Errors: 400 missing process/candidate for mode · 403 lacks Manage Onboarding (ref §3.7) · 409 open instance already exists for candidate (MSG-ERR-DUP-INSTANCE) · 422 validation (field-level per §6.2). Idempotency: client may send Idempotency-Key; a duplicate key returns the original 201. Side effects per §8.5.
PUT /api/v1/onboarding/instances/{id}/form-responses — auto-save (FR-M02-002 / DO19)
Request: { responses: [ { field_name, field_value } ], save_reason:‘AUTOSAVE’|‘MANUAL’ }
Response 200: { saved_at: timestamp, draft_count, server_validation: [ {field_name, code} ] }
Behaviour: upserts onboarding_form_responses at field_status=DRAFT; never blocks on validation (errors returned inline, save still succeeds) per FR-M02-002 edge case. Auth: candidate on own case only (403 otherwise). Rate limit: write tier per §6.3; auto-save batches every 30s (DO19) so it stays within limits. saved_at powers the “Last saved at” indicator (OPEN-FS-M02-14).
POST /api/v1/onboarding/instances/{id}/complete — admin completion (§8.5 ADMIN_REVIEW → COMPLETED)
Request: { confirm_bgv_in_progress?: boolean } // required true if BGV not clear (DO17)
Response 200: { state:‘COMPLETED’, employee_id, m01_lifecycle_state:‘ACTIVE’ }
Pre-conditions enforced server-side (referenced, not restated): all Sign-Off acknowledgements ACKNOWLEDGED (FR-M02-003) and all mandatory workflow tasks COMPLETED (DO08). 409 PRECONDITION_NOT_MET with the failing gate(s); 422 if confirm_bgv_in_progress omitted while BGV incomplete (DO17 — warn-not-block). Emits ONBOARDING_COMPLETED (§9.5 / MSG-OB-COMPLETED) and the M01 handover event.
POST /api/v1/bgv/results — inbound vendor webhook (FR-M02-004)
Request (vendor): { vendor_reference, onboarding_instance_id, checks:[ {check_code, status, report_url?} ] }
Response 200: { accepted: true, updated: n }
Auth: vendor API key + HMAC signature (integration_credentials §4.14.6). Idempotent on (vendor_reference, check_code) — re-delivery updates in place. Populates bgv_results §4.7.7; DISCREPANCY rows surface on 2.7. Emits BGV_RESULT_RECEIVED (§9.5 / MSG-OB-BGV-RESULT). Manual-entry fallback uses 4.2 report endpoint when the vendor is unavailable (FR-M02-004 edge case).
POST /api/v1/bgv/results/{id}/disposition
Request: { disposition: ‘RETAIN’|‘INVESTIGATE’|‘INITIATE_SEPARATION’, notes: string } // notes mandatory
Response 200: { disposition, disposition_by_user_id, disposition_at }
Auth: BGV review capability flag (§3.10) — 403 FIELD_ACCESS_DENIED otherwise. INITIATE_SEPARATION post-completion triggers the M03 workflow with the BGV reference (FR-M02-004). Note the enum here is the BRD §4.7.7 vocabulary; the prototype’s resolution options differ — OPEN-FS-M02-09 must reconcile before build.

Reflects the Batch-5 review of the candidate (pre-joining) surface against the clickable prototype (v2). Complements — does not replace — the body of this FS. The candidate surface is the dedicated candidate role (Welcome · My onboarding form · Document upload · My offer letter · Pre-joining info).
Offer acceptance
The candidate’s offer letter supports Accept and Decline in-system, in addition to PDF download. Accept confirms the offer terms and joining date and unlocks onboarding; Decline requires a reason and notifies the recruiter. Offer acceptance is the entry gate to the pre-joining flow.
Document upload — clusters, categories and verification
Required-document upload is classified by the Document Categories (Personal Identification, Education & Training Certificates, Employment Documents, etc.) and is presented as part of the candidate’s Verification Package, which feeds Background Verification (BGV) (BGV is enabled). OCR is off, so candidates enter document details manually where prompted. The enabled document clusters (Sign-off / Undertaking / Reference) and the Verification Package govern which documents appear.
Buddy
The onboarding buddy is enabled and is surfaced to the candidate on the pre-joining screen (buddy name, role and contact, with an introduction action), so the new hire can connect before joining.
Configuration-driven behaviour
The candidate surface tracks onboarding configuration: the onboarding form is mandatory with explicit save (auto-save is off); E-Verify and ID-Verification packages are disabled and are correctly absent from the candidate experience; and the Welcome-page company name is bound to the legal entity (Display Group Company as Company Name = No).
Joining-date changes — admin only
Joining-date changes are performed by HR / admins only. The candidate has no self-service joining-date change request on the pre-joining screen; any reschedule is initiated and approved by the appropriate admin.
Manager-role review (Round 3)
Probation extension UX: the manager Probation decision improves the Extend flow — an Extend by selector (1/2/3 months) renders a live new-end-date preview before submission, and the Extend action is disabled until a period is selected. Bounds and defaults are sourced from Probation configuration (Show in Probation Extension, Extend Confirmation).
