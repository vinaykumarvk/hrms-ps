2.9 Candidate & Pre-joining Portal (Candidate role)
References: BRD §5.7 FR-M08-002/004/005/010/015 · §8.6 (candidate state machine) · Vision §3.1 (Candidate mandate) and §2.2/§2.6 (external auth, consent) · prototype candidate panel (candidate-profile, document-upload, offer-letter; pre-joining/onboarding screens are M02) · config: duplicity_check_settings §4.9.12, Candidate_Auto_Numbering, Custom_Source, Verification Status master, Candidate Decision/Archival reasons, ReasonList candidate flags. The Candidate is an external party; this section authors the candidate-facing recruitment surface and the hand-off to M02, and does not restate M02 pre-joining screens.
The Candidate role has two consecutive states, both served through an external portal — never the live HRMS:
Candidate state (recruitment) — from application through offer decision. Surfaces: careers application, candidate profile, application-status tracking, document upload & BGC consent, offer accept/decline.
Pre-joining state (post-offer-acceptance) — handed to M02. Surfaces: pre-joining checklist, onboarding form, stakeholder workflow forms, buddy, policy/sign-off documents, Chat Agent. These are specified in M02 (FR-M02-001/003, Appendix J) and referenced here, not restated.
2.9.1 Portal boundary & authentication
Aspect
	Specification

Identity
	External candidate identity, separate from employee SSO. Created on first careers application or on offer release. No employee record exists until offer acceptance triggers M01 creation (FR-M08-005).

Access ceiling
	Portal-only. No access to any live HRMS module, employee directory, org chart, other candidates, internal notes, recruiter feedback, CTC bands, or internal decision/archival reasons. PII is own-record only.

Auth mechanism
	Email + OTP (passwordless) for the external candidate portal — a candidate identity separate from employee SSO. Session policy per Vision §2.2 (short-lived token, server-side refresh with revoke); account recovery via email OTP. No password store for candidates.

Consent
	DPDPA consent captured at application and at BGC initiation; consent records are immutable (supersede, never delete) per Vision §2.6.

2.9.2 Careers application & candidate profile
Screen: candidate-profile (+ external careers entry). FR-M08-002/003/008.
Entry channels: Careers Page (external self-apply), Refer (employee referral link), External Recruiter Portal (vendor submission). IJP is out of scope (CFG-002).
Application fields are driven per job by job_application_field_config (§4.9.17). Configuration ownership: the Org Admin maintains the global candidate / custom-field catalog (fields that may exist); the Recruitment Admin selects which of those fields appear on a given job's application form and marks each enable/mandatory/default, at Create Job → Job Application (Recruiters cannot configure this). The per-tenant default field set is a tenant configuration action, not a code dependency.
On submit: candidate record created with CAN number from Candidate_Auto_Numbering (prefix + next number, keyed by Company / Employee Type / Region); source stamped from Custom_Source / source type. State → APPLIED (§8.6).
Duplicity / re-application (duplicity_check_settings §4.9.12): duplicate detection on the configured key fields; re-application blocked until Number Of Days Before Reapplication By Candidate elapses; Allow candidate to apply for multiple positions governs concurrent applications (separately for Other Sources and External Recruiter). Override is limited to Super Admin / Hiring Lead / permission holders.
Candidate may edit own profile only while in pre-submission/early stages as configured; resume parsing may pre-fill fields (candidate confirms).
2.9.3 Application-status tracking
Screen: candidate-profile (status view). FR-M08-016.
Candidate sees own progress across the job's configured hiring stages (§8.6) — e.g., Applied → Screening → Interview → Offer — at the granularity the tenant exposes.
Internal decision/archival reasons (Candidate Rejection, Candidate On Hold, Offer Withdrawal, Job Archival, Job Closure, Candidate Decline Offer) are hidden from the candidate unless the reason's Hide Reason for Candidate flag is off (ReasonList master).
Candidate reminder e-mails are governed by Reminder Email to Candidate (ReasonList) and the onboarding reminder cadence (every X days) where applicable.
2.9.4 Document upload & BGC consent
Screen: document-upload (FR-M08-010 verification set; FR-M02-003 vault). Verification Status master.
Candidate uploads the mandatory document set (PAN, Aadhaar, education certificate, relieving letter, recent salary slips, bank proof, photograph) per the document-review checklist; each item shows category and status.
Verification is performed by Recruiter (first-pass flag) / Recruitment Admin / HR Admin — the candidate cannot self-verify. Status values come from the Verification Status master: Documents Awaited · BGV In Progress · Completed Successfully · BGV Failed · On Hold · VerificationInitiated · VerificationCompleted.
BGC: candidate gives explicit BGC consent before initiation; BGC is enabled tenant-wide via Enable BGV (Onboarding settings). Release 1 runs BGC in-house / manually — no external BGC-vendor integration is in scope. Status is tracked via the Verification Status master; external-vendor integration is a later-phase enhancement.
PII uploaded by the candidate is encrypted and masked in downstream display per Vision §2.4/§2.5.
2.9.5 Offer letter — accept / decline
Screen: offer-letter (FR-M08-004/015).
Candidate views the released offer (read-only), downloads the PDF, and acts: Accept (countersign → POST /api/v1/offers/{id}/countersign, Auth: Candidate portal) or Decline (reason captured; event Candidate Decline Offer). No candidate counter-offer / negotiation is in scope — accept or decline only.
Offer is visible to the candidate only when its lifecycle state is Approved/to-share → Pending with candidate (§8.7a); earlier states are not exposed.
On Accept: offer lifecycle advances to employee-movement; /movement/approve triggers M01 employee creation + M02 pre-joining (FR-M08-005). Candidate transitions from Candidate state to Pre-joining state.
Offer expiry and withdrawal (Offer Withdrawal) are system/recruiter driven; on expiry the candidate can no longer act.
2.9.6 Hand-off to pre-joining (M02)
At acceptance the candidate is handed to the M02 pre-joining portal (FR-M02-001): pre-joining checklist, onboarding form (incl. BGV form variants), stakeholder workflow forms (Appendix J), buddy introduction, policy/sign-off documents, and the Chat Agent. These screens are specified in M02 and are not restated here. The candidate retains portal-only access throughout pre-joining; no live HRMS access is granted until onboarding completion activates the employee record (M02 completion criteria).

Page — PrimeSoft HRMS Functional Specification # Prototype Sync Addendum — Batch 7: Employee-as-applicant review (June 2026)
Reflects the Batch-7 review of the employee recruitment surface (IJP, referrals, interviews) against the clickable prototype (v2). Complements — does not replace — the body of this FS.
Internal job postings (IJP) — not in scope
IJP is not in scope. The employee IJP screens (internal-jobs browse and “My IJP applications”) and the self-service entry have been removed; the IJP reapplication field has been removed from duplicity configuration; and IJP references in the employee profile, the leadership AI chat, and recruitment analytics have been cleared. The duplicity configuration that enabled IJP application (Allow Employee To Apply For Multiple Positions Via IJP; reapplication-after-days) is to be set to No / disabled in the system. The IJP posting channel on the job-creation screen — the Careers / IJP / Refer channel matrix, including the IJP view / mandatory columns — is to be removed in the Recruitment-Admin pass. Internal mobility, where needed, is handled outside IJP through the recruiter / HR process.
Referrals
Employee referral submission uses a candidate-detail form — candidate name, email, phone, role / requisition, source, and resume — rather than a bare action. Duplicate applications are checked against the duplicity settings, and re-referral is permitted only after the configured window. The referral routes to Talent Acquisition.
Interviews
The employee’s “My interviews” surface is view-only (upcoming and history); join-link and reschedule actions are not provided to the employee.
IJP fully removed from recruitment (out of scope)
Internal Job Postings (IJP) are out of scope for this tenant. The Create Job screen no longer offers IJP as a posting channel — the IJP posting-channel row, the IJP channel pill, the IJP view / IJP mandatory columns in the field-display matrix, and the IJP entries in the job-name label and the resume-parsing list have all been removed. Posting channels are Careers and Refer only. No IJP references remain anywhere in the product (verified: zero occurrences). The corresponding tenant configuration action is CFG-002 (disable IJP multi-position and reapplication settings).
