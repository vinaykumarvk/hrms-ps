2. Screen Specifications
Each screen: purpose, the requirement/BRD ref it satisfies, layout regions, field behaviour, the five states (§3 Foundation FS), actions → contracts (§4) / message ids (Foundation §5 / §8.2). Visual styling is the design system’s.
2.1 doc-settings — Global Document Settings (Org Admin)
Purpose: module-wide toggles, global sign-off + acknowledgement text, storage/encryption (Req A.1–A.3). Regions: toggles · sign-off text editor · acknowledgement text editor · storage/encryption summary (read-only, per P05). Fields: HR-policy sign-off text (VAL-REQUIRED, VAL-LEN), HR-letter acknowledgement text (VAL-REQUIRED), block-HR-policy-on-mobile (toggle), CTC font/size/padding (letter rendering). Actions: Save → PUT /api/v1/document-settings.
2.2 policy-library / 2.3 policy-detail — Policy Library (Document Admin / HR Admin)
Purpose: register, version, publish, assign policies; tag forms (Req B, F.4). List regions: filter by category/status + “New policy” + “Assign policy”. Detail: master attributes (name, category VAL-ENUM, owner, effective date VAL-DATE, version), lifecycle state (DRAFT→PUBLISHED→ARCHIVED per B.3), assignment (UAG/role scope per F.1), tagged sign-off form (W.2 form id). Publish triggers POLICY_PUBLISHED notification (§9.6) to in-scope employees. Actions: New/Edit → POST/PUT /api/v1/policies; Publish → POST /api/v1/policies/{id}/publish; Assign → POST /api/v1/policies/{id}/assignments.
2.4 doc-templates — Letter Template Builder (Letter Admin flag · Document Admin / HR Admin)
Purpose: author/manage letter templates + merge-field bindings + versioning (Req D.1–D.2; RBAC §4.3 Letter Admin). Regions: template list (inventory: LTR_OFFER, LTR_APPT, LTR_NDA, LTR_CONF, LTR_CONFM, LTR_PROBX, LTR_INC, LTR_PROMO, LTR_TRLOC …) · template editor (body + merge fields ${…}) · signature config (D.3) · activate/publish. Merge fields validated against the entity merge catalogue (Req D.2); unknown token → ERR (M11 slice). Actions: POST/PUT /api/v1/letter-templates, POST …/{id}/publish.
2.5 letterheads — Letterhead & Signer Configuration (Org Admin / HR Admin)
Purpose: letterheads (HTML + DOCX), default signing authorities (up to 4) and signatures (Req D.3; Self-Generate Settings). Fields: letterhead HTML/DOCX upload (VAL-FILE), signer 1–4 (employee picker), signature image per signer (VAL-FILE). Actions: PUT /api/v1/letterheads.
2.6 generate-letter — Generate Letter (HR Admin; bulk per D.4)
Purpose: generate a letter for one or many employees from a template, with serial numbering and signature (Req D.4). Regions: template select · recipient select (single/bulk) · preview (merged) · serial (${SYS.letter_serial} per name-format) · generate. Bulk generation runs as a background job (§8.1). Generated letters write to the employee vault and trigger LETTER_ISSUED notification. Actions: POST /api/v1/letters (single) / POST /api/v1/letters/bulk (job).
2.7 employee-vault — Employee Document Vault
Purpose: per-employee document repository across the 18 document types (Req Part C), categorised, version-chained (Part H.1), with retention class. Regions: category tabs · document list (type, version, status, retention) · upload/replace · view (PII-masked per tier). Field behaviour per the vault access matrix (Req C.2) — projected in §6. Sensitive uploads route to the M01 sensitive-field approval gate (P01). Actions: POST /api/v1/employees/{id}/documents, GET …, POST …/{docId}/versions, POST …/{docId}/disposal.
2.8 signoff-tracker / 2.9 signoff-pending-report — Sign-off & Acknowledgement (Req E)
Purpose: track policy/letter sign-off tasks, capture acknowledgement, handle decline, and surface the pending report (E.1–E.4). The prototype shows the aggregate (“412 sign-offs · 218 policy · 194 letter”). Sign-off task list (status, due, employee), acknowledgement record (timestamp, version acknowledged), decline path (reason → routing per E.3). Pending report filterable by policy/letter/UAG. Actions: POST /api/v1/signoffs/{id}/acknowledge, POST …/{id}/decline; report GET /api/v1/signoffs?status=PENDING.
3. Interaction & Navigation Flows
References: BRD §5.12.10 (4 Document-Issue flows), §8 (lifecycle state machines), M11 Req Part G/K. The state machine is referenced, not redrawn; this shows which screen/job drives each transition.
Four document-issue flows (BRD §5.12.10), each mapping a lifecycle event → letter generation → vault → sign-off: 1. Onboarding sign-off cluster — M02 completion → generate LTR_APPT/NDA/LTR_CONF (W.1 onboarding workflow) → vault → sign-off tasks (E.1). 2. Probation confirmation/extension — M01 lifecycle Active(probation)→Active(confirmed) → LTR_CONFM / LTR_PROBX on HR Admin action. 3. Lifecycle letters — increment (LTR_INC), promotion (LTR_PROMO), transfer (LTR_TRLOC) generated on the respective approval event (M09/M10/M01); LTR_INC/LTR_PROMO depend on M10 Compensation — Phase 2 (see §10). 4. Separation/experience letter — M03 separation → LTR (experience/relieving) → terminal vault version. Policy Sign-Off action embeds in any workflow stage (W.1; Req G.1); lifecycle-driven generation per G.2; M02 cluster delegation per G.3.
4. API Contracts
Inventory referenced from BRD §6.4; full contracts authored here. Auth/idempotency/pagination/error-envelope per Foundation §1. Errors reference Foundation/M11 message ids.
POST /api/v1/letters — generate a letter (Req D.4) Request: { template_code, employee_id, merge_overrides{}, letterhead_id, signers[] } Response: { letter_id, serial, document_id, pdf_url } Errors: 403 (ref P02) · 404 template/employee · 409 duplicate (Idempotency-Key) · 422 unknown merge token / missing required merge field (VAL per Req D.2)
POST /api/v1/letters/bulk — bulk generate (background job JOB-M11-BULKLTR §8.1) Request: { template_code, employee_filter{} | employee_ids[], letterhead_id } Response: { job_id, count } (progress polled; completion notifies issuer)
POST /api/v1/employees/{id}/documents — upload to vault (Req C) Request: multipart { document_type, file, effective_date? } (VAL-FILE; PII tier per Appendix B) Response: { document_id, version, status } Errors: 403 (vault matrix §6) · 422 type/retention invalid · 409 sensitive-pending (M01 gate)
POST /api/v1/signoffs/{id}/acknowledge | /decline — sign-off engine (Req E) Request: acknowledge { version_acknowledged } · decline { reason (VAL-REQUIRED) } Response: { signoff_id, status } Errors: 403 · 409 already-actioned · 422 reason required (ERR-REASON-REQ)
POST /api/v1/policies + /{id}/publish + /{id}/assignments — policy library (Req B) POST/PUT /api/v1/letter-templates (+ /{id}/publish) — template builder (Req D) PUT /api/v1/letterheads · PUT /api/v1/document-settings — config (Req D.3 / A)
5. Validation
Reference Foundation §2 catalogue ids; author only M11-unique rules.
Referenced: VAL-FILE (uploads — type/size/scan), VAL-REQUIRED, VAL-LEN, VAL-ENUM (category/type), VAL-DATE (effective/retention), VAL-CONSENT (acknowledgement). M11-unique (authored here): VAL-M11-MERGE — every ${token} in a letter template must resolve against the merge-field catalogue (Req D.2); unknown/unbound token blocks publish. VAL-M11-RETENTION — a document’s retention class (Req H.2) governs disposal eligibility; disposal blocked before the window. VAL-M11-SIGNER — generate requires the template’s configured signer set (D.3) to be resolvable (active employees with signatures).

Prototype Sync Addendum — Batch 4: Employee-role Documents, letters & policies review (June 2026)
Reflects the Batch-4 Employee-role review against the clickable prototype (v2). Complements — does not replace — the body of this FS.
Letter acknowledgment
HR letters that are flagged acknowledgment-required expose an Acknowledge action in the employee’s “HR letters issued to me” list. Acknowledgment opens a confirmation showing the configured HR Letter Acknowledgment Text (“I confirm that I have read and understood this document”) and records actor and timestamp against the letter. Download remains available on every letter regardless of acknowledgment state.
Policy acknowledgment — confirm only, no decline
The employee acknowledgment queue (policy-ack) acknowledges policies via a confirmation showing the configured HR Policy Sign-Off Text (“I confirm that I have read and understood this document”). The employee cannot decline a policy — acknowledgment is confirm-only; there is no employee decline path. Confirmation records actor and timestamp for HR and the HRBP. “Read” opens the document first.
Document categories
Employee document upload and the official-documents view are classified by the four Document Categories from the master: Personal Identification, Employment Documents, Education & Training Certificates, and Health, Safety & Compliance. The upload category list is bound to that master rather than an ad-hoc list, and official documents are presented under their category.
Single acknowledgment surface
policy-ack is the single action queue for pending acknowledgments. The policies library is read-only (view only); any item still pending acknowledgment links the employee to the queue rather than offering a second, parallel acknowledge action.
Letter requests
Employee letter requests (salary certificate, employment letter for visa/loan, experience letter, address-proof letter) are raised to HR and read as tracked requests with a stated turnaround and a notification on issue. Employees do not self-generate letters — self-generation remains restricted to the configured permission holders.
Out of scope / deferred
Payslips and payroll are out of scope (no payroll module). Visa / work-permit document capture is Phase 2.
