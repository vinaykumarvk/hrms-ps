How to read this specification
References BRD v6.9 (authoritative for all requirements) · Prototype v20.7 (authoritative for the screen layer) · this FS (the build layer only)
This Functional Specification adds the build layer for Module M01 — Employee Master: screen layouts, complete API contracts, field-level UI behaviour, validation formats, per-screen role projection, interaction states, and the operational layer (scheduled jobs, message catalogue, dashboard widgets). It is written against BRD v6.9 and Prototype v20.7.
Single source of truth. Anything the BRD already fixes — a business rule, a data field, an NFR target, a permission-matrix cell, a state transition, a notification trigger, a glossary term — is referenced here by section number, never restated. If a fact appears to be missing, the BRD is authoritative; this FS points to it.
Screen provenance. Every screen specified here traces to a prototype screen id (the prototype’s data-page attribute). No screen is invented. Where the prototype lacks a screen the BRD implies, or where prototype and BRD disagree, the mismatch is recorded in §7 with a proposed resolution marked PROPOSED — confirm before build — it is never silently decided in the body.
Document architecture note. The author’s default is a shared Foundation FS (cross-cutting build content) plus one per-module FS. Because only the Employee module was requested, the cross-cutting items that M01 needs — the shared validation catalogue (§5), the M01 scheduled jobs and message catalogue (§8), and the menu-entitlement slice (§6.2) — are carried inline here and flagged for promotion to a Foundation FS when sibling module specs are authored, so they remain singular and do not drift.
Legend. In field tables: control = the UI element; every other column is a reference to its single source. In RBAC tables: V = visible · M = masked · H = hidden · E = editable · AR = approval required (per BRD §3.9 legend).

2.1 Employee Self-Service Profile — my-profile
Employee-review notes (v1.2). (a) Promotion-readiness is not shown on the employee self-view — it is a calibration/manager output (M09) surfaced only to manager/HR/calibration roles. (b) The manager’s peer list is not shown on the employee profile. (c) The HRBP appears as a single card (de-duplicated). (d) Benefits provenance: PF / EPS / ESIC / Gratuity / LWF / PT records are entered and maintained by HR Admin; values bind to the statutory masters; billing rate is masked from Self. (e) Document types behind the Statutory & Documents tabs are listed in the Document-Types appendix (Document Categories + template formats + National-ID document set) — see M11 (single source) for the full register and per-type who/when/source.
References Satisfies FR-M01-003/004/007/011/014/015/016/019 · Renders employees §4.4.1 + sub-entities · RBAC §3.9 (self column) · Prototype: my-profile
Purpose. The employee’s single canonical record, presented as a tabbed hub. One shared detail definition renders here (self tier), in hr-employee-detail (full tier), and in employee-detail (read-only tier) per FR-M01-020 — the access tier is resolved at render time from the viewer’s role.
Layout regions. (a) Identity header — photo/initials avatar, display name, lifecycle-state badge, designation·department·pod, employee ID, DOJ + tenure, reporting-to, location·work-type, plus Download PDF and Edit-personal-details actions; (b) KPI strip — leave balance, attendance (90d), last review, profile-complete %; (c) left tab rail; (d) tab content pane.

Complements BRD v6.9 — references, does not restate · Page of # Prototype Sync Addendum — Batch 1: Employee-role review (June 2026)
Reflects the Batch-1 Employee-role review against the clickable prototype (v2, M11-synced). Complements — does not replace — the body of this FS.
Employee Directory & mini-profile (distinct from the full master)
The Employee Directory is a peer surface, separate from the full Employee Master roster. It shows the standard fields only (RBAC §11.2): name, photo/avatar, designation, department, official email, official phone, office location, reporting manager — Active employees only; separated/absconded/pre-joining are excluded. A directory row opens a read-only mini-profile (DM-PRO12) limited to those fields — not the full employee detail. Recruiters see the reduced four-field view (§8.1). The full master roster (all fields, edit, Add Employee) is the HR-Admin-tier employee-master screen.
Org chart (all roles)
The organisation chart is a standard menu item available to every role (RBAC §11.1); node fields are name, photo, designation, department, reporting manager; a node opens the same read-only mini-profile.
Config-driven National-ID section
The statutory-ID set on the profile is configured per geography via the tenant National-ID configuration (e.g., PAN/Aadhaar for India, Social Security for Thailand). The profile renders the configured ID types and aliases — it must not hardcode an India-only set. Values remain masked in the employee’s own view; changes route to HR approval (E·AR).
Consent & privacy self-service
The employee can view their consent history (records are immutable — superseded, never deleted) and withdraw optional consent, which triggers the data-erasure workflow for the related non-statutory data; statutory processing is unaffected (BRD FR-M01-003). The employee may export their full record with PII unmasked.
Custom fields on the profile
Organisation-configured custom fields appear in the relevant profile sections per the CustomFields configuration (Display-in / FOR / Is-Editable) — they are config-driven, not fixed.
Employee-initiated sensitive changes (prototype now reflects FS §2.1/§2.2/§2.14)
Tier-1 ID changes (PAN/Aadhaar/Passport/DL) and bank changes surface to the employee as “Request change → HR” (sensitive-changes queue; penny-drop for bank). Personal mobile/email edits are flagged as HR-verified (Tier-2). These behaviours were already specified; the prototype now exposes the employee-side entry points.
Manager reportee detail — field visibility (L1)
When an L1 manager opens a reportee’s detail, they see the reportee’s internal employment history (movement: designation, department, manager, event) and the prior-employment history declared at joining (employer, role, dates). They do not see the reportee’s prior Last CTC or BGV status — those two fields are restricted from the L1-manager view. The reportee detail otherwise inherits the same role-scoped field gating as the self-profile.
HOD department-employee detail — read-only, scoped, salary permission-gated
The HOD “Department employees” roster drills into a read-only, department-scoped employee detail — not the HR-Admin full profile. It exposes overview, internal employment history, performance (read-only), an attendance & leave summary, education and the competency profile, and carries no edit or transaction actions. It does not expose Tier-1 identifiers, statutory IDs, bank details, BGV or the audit log. Compensation (salary / CTC) is permission-gated: only HODs granted the Compensation View permission see the compensation card; HODs without it do not see it at all. This permission is configured per HOD (some HODs may view salary, others may not).
HOD dashboard — department deep-links
The HOD dashboard surfaces an Escalations & skip-level tasks widget and a Department-lens widget whose quick-links deep-link to the department oversight pages — Headcount plan to department headcount, Department org chart to the org chart, and Calibration session to department performance. These are navigation shortcuts to already-specified oversight screens; escalation task actions and backfill requests are out of scope for this screen.
HRBP assigned-employee detail — scoped (no compensation, no audit)
The HRBP “My assigned employees” roster drills into an HRBP-scoped employee detail, not the unrestricted HR-Admin profile. It exposes the employment summary, personal information (Tier-1 identifiers masked), statutory IDs (masked), the §3.9 sensitive categories the HRBP is granted (disability declaration, visa / work authorisation, dependents / nominees), BGV status, internal employment history, education, documents, and a leave & attendance summary. Compensation (CTC / salary / bank) and performance are hidden from HRBP and the audit log is admin-only — neither appears on the HRBP view.
HRBP module views — read-only scope
HRBP’s “Modules — view” and the probation / BGV task items are read-only oversight surfaces. Where the prototype reuses another role’s screen, HRBP must be RBAC-gated to view only:
BGV status — HRBP views verification status; the Modify / Save / Sync actions on the BGV console are restricted to the BGV / Onboarding admin.
Probation — HRBP views probation status; the Confirm / Extend / Separate decision actions belong to the Manager (confirm) and HR Admin (approve), not HRBP.
Performance reviews — not accessible to HRBP. Performance is not an HRBP function; review / people drill-downs do not expose performance data and resolve to the HRBP-scoped employee detail.
Recruitment — read + comment only (FR-M08 · A2); Documents — acknowledgement status, read-only.
Manager-role review (Round 3)
Reportee profile (manager scoped view): the Attendance, Leave and Performance tabs are relocated out of the reportee profile to the dedicated Team attendance, Team leave and Goals & reviews screens — the data remains available there, it is not removed. The scoped reportee view retains Overview, Employment history, Skills & education, Org chart and Feedback & notes.
Probation decision (manager): the Extend action gains an explicit Extend by control (1/2/3 months) with a live recalculated probation-end-date preview; Extend is disabled until a period is chosen, and re-triggers the decision task 15 days before the new end date.
Manager-role review (Round 3 follow-up)
Reportee view = employee self structure. The manager's reportee record now mirrors the employee's own profile: Personal, Employment (incl. Project history), Statutory & benefits, Qualifications & experience, Documents, plus Attendance, Leave and Performance as tabs in the employee-context view. This supersedes the Round-3 item-6 tab relocation and the prior §3.9 "manager = HOD narrow scope" restriction on the reportee record.
No dilution except intentional masks. Information matches the employee's own view; the only deliberate masks are full Aadhaar/PAN, bank account number and statutory IDs (restricted to the employee and authorised HR/Finance roles, audit-logged).
Project history is added to the Employment tab in both the self profile and the reportee view.
Manager-role review (Round 3 follow-up B)
Education placement corrected. Education records belong under Qualifications & experience, not Employment. Education has been moved out of the Employment tab into Qualifications & experience in the manager reportee view and the HR-Admin employee record; the HOD view already grouped it with Skills. This keeps the self, manager, HOD and HR-Admin profile structures consistent.
