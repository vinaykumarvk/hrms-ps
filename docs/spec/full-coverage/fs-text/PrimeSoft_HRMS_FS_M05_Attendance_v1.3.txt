How to read this document
This Functional Specification is the build layer on top of the PrimeSoft HRMS BRD v7.4 BASE. It does exactly one job: it adds the screens, complete API contracts, validation, per-screen role projection and interaction states that the BRD deliberately leaves out — while referencing the BRD for every business rule, data field, decision, permission and NFR the BRD already owns. The governing principle is single source of truth: a fact lives in exactly one document.
Two visual conventions are used throughout. Muted italic text in this colour is a reference — it points to a fact owned by the BRD (e.g. BRD §4.6.2) or by the Foundation FS, and is never restated here. Upright text is content authored by this FS. Every section opens with a References band listing the BRD sections, prototype screens and Foundation FS sections it builds on, so any fact is traceable to its origin.
Where the prototype and the BRD disagree, or where neither covers something needed to build, this FS does not silently choose. It records the gap in §7 (Open Items, Conflicts & Recommendations) with a named owner and a proposed resolution marked PROPOSED — confirm before build. The BRD wins until an open item is resolved.
Naming: entity and field names are quoted verbatim from the BRD data model (§4.6) so engineering can bind screens to columns without translation. Screen ids in §2 match the prototype data-page attribute exactly.

2.1 My Attendance
Screen id: attendance* · Role: Employee (own) · Platform: web + mobile*
References — FR-M05-001 (both-punch present rule) · FR-M05-018 (Clock-In/Out) · FR-M05-019 (Check-In/Out) · FR-M05-012 (register) · FR-M05-017 (OT indexing) · FR-M05-009 (infractions) · entities attendance_records, attendance_requests, overtime_slabs §4.6.4/.5/.13 · RBAC §3.7.1 Own attendance = E · widget §10.2 My Attendance
Purpose. The employee’s single attendance home: punch action, month-to-date metrics, the attendance register, the employee’s own requests, and read-only Overtime and Infraction views. The capture buttons shown are governed by the employee’s assigned modality (FR-M05-020 / attendance_modality) — Clock-In only, Check-In only, or both. Never the platform.
Layout regions
Action bar — primary punch button (CLOCK IN / CLOCK OUT and/or CHECK IN per modality), current-punch status line, links: Request regularisation, Request comp-off.
Metric strip — Present days MTD, WFH MTD, OT this month, Continuous working days. Each is a computed read-only tile.
Tab region — Register · My requests · Overtime · Infractions.

For each transition it names the screen that drives it and the job (Foundation FS) that drives system transitions. The approval flows and SLAs themselves are owned by §5.12.5 (FLOW-AT-001…007).

3.2 System-driven transitions (jobs, not user actions)
These transitions are driven by scheduled jobs (specified in the Foundation FS; M05 slice in §7 of this document), not screens:
Daily attendance close classifies each day (PRESENT/LATE/INCOMPLETE/ABSENT…) and feeds infractions (FR-M05-009) — JOB-M05-CLOSE.
Absconding detection sets lifecycle_state=ABSCONDED after 7 consecutive calendar days (FR-M05-005) — JOB-M05-ABSCOND; surfaces on the M03 absconding queue (§2 boundary).
Period lock sets is_locked=TRUE at the payroll cutoff (FR-M05-006) — JOB-M05-LOCK; surfaces on Attendance Lock §2.10.
LOP report generates and emails the LOP feed (FR-M05-014) — JOB-M05-LOP.
3.3 Cross-screen navigation
My Attendance register row (INCOMPLETE/ABSENT) → Request Regularisation pre-filled with date + missing-punch type.
Team Attendance row action → Attendance Approvals filtered to that reportee’s pending request.
Outside-fence Check-In → Check-in Approvals queue (L1) → on approve, returns the employee’s record to PRESENT off-site tag.
Attendance Lock pending-items → Attendance Approvals (resolve Stage-1 items before lock).

4.1 POST /attendance/punch

Request
{
“action”: “CLOCK_IN | CLOCK_OUT | CHECK_IN | CHECK_OUT”,
“modality”: “CLOCK | CHECK”, // per FR-M05-020 assignment
“captured_at”: “2026-05-26T09:02:14Z”, // client second-precision
“geo”: { “lat”: 12.9698, “lng”: 77.7500, “accuracy_m”: 18 }, // CHECK only
“selfie_document_id”: “{uuid}”, // optional, CHECK only
“source_ip”: “10.0.0.42”, // CLOCK only, for whitelist check
“device_id”: “BIO-BNG-01” // optional
}
Response (2xx)
{
“attendance_date”: “2026-05-26”,
“status”: “PRESENT | INCOMPLETE | OUT_DUTY”,
“clock_in_time”: “2026-05-26T09:02:14Z”,
“clock_out_time”: null,
“late_by_minutes”: 2, // zero-grace per FR-M05-001
“clock_in_in_geofence”: true,
“requires_approval”: false, // true when outside-fence CHECK
“modality_used”: “CHECK”
}
Errors
400 malformed payload / missing action.
403 modality not assigned to employee, or CLOCK from non-whitelisted IP (FR-M05-018) → FIELD/IP_ACCESS_DENIED. Reference RBAC §3.7.1 / §7.4.3.
409 duplicate punch — already clocked in (FR-M05-018) → MSG-AT-DUP.
422 GPS denied / selfie required-but-missing (FR-M05-019) → VALIDATION_FAILED.
Idempotency / pagination: Idempotent on (employee, action, captured_at minute) — replays within the same minute return the existing record, not a second punch (handles mobile retry). Prototype Sync Addendum — Batch 3: Employee-role Attendance review (June 2026)
Reflects the Batch-3 Employee-role Attendance review against the clickable prototype (v2). Complements — does not replace — the body of this FS.
Attendance regularisation
The regularisation reason list is drawn from the Attendance Reasons master (typed: Regularisation / Out-duty / Shift-change), not hardcoded. Reason and comments are both mandatory (Attendance settings), and regularisation is permitted only within the configured window (“During fixed duration” / defined days from cycle end). The correction type (missed punch in/out, wrong time, etc.) remains a separate structural field.
Overtime — not in scope
There is no overtime feature. The employee attendance page does not display overtime, there is no overtime request, and planned overtime is not offered. The earlier Enable Planned Overtime vs Allow self planned-OT configuration conflict is therefore moot. Overtime-related approver and configuration surfaces — the Overtime approvals queue, the OT indexing slabs configuration, and the Overtime navigation item — have been removed.
Comp-off credit
Comp-off remains in scope. The employee raises a comp-off credit request based on working on a weekly-off or holiday (worked date + hours + reason); comp-off is credited on approval per the comp-off policy (full / half day, lapse). Availing comp-off is via the leave-application screen (see M04). No overtime is involved in either path.
Infraction display
Infraction history is gated on Enable Infraction Framework and is hidden when the framework is off (off for this tenant). Basic late-mark counts (within grace) remain visible independently of the infraction framework.
Shift-change — not employee self-service
A shift-change request is initiated by the Manager or Attendance Admin and approved by HR Admin; it is not an employee self-service action and is therefore absent from the employee screens by design. Shift master eligibility (Show For Shift Change Request) and the “Shift Change” reason type support the initiator-side flow, specified in the Manager / Attendance-Admin scope.
Clock-in / check-in capture
Clock-in / clock-out is modelled as a punch state (IP-verified against the attendance IP networks). Check-in, selfie capture and geofencing are configuration-gated (Enable image capture (selfie), Disable Clockin / show Check In, Enable geofencing) and are off for this tenant; the build must keep clock-in and check-in a single capture component switched by these flags rather than two hardcoded paths.
Manager team views inherit attendance gating
The manager’s Team attendance view inherits the same configuration gating as the employee attendance page: it shows no overtime column (no overtime feature) and no infraction column (infraction framework off for this tenant), surfacing presence, punch-in / punch-out and late-mark (within-grace) counts only. A single configuration change must move both the self-view and the manager team view.
Manager attendance approval — reject reason
Rejecting an attendance-regularisation request requires a mandatory reason (config: Reject reason mandatory for attendance-related requests = Yes). Shift-change is not present in the manager’s attendance-approval queue — it is initiated by the Manager / Attendance Admin and approved by HR Admin (as specified above).
Check-in approvals — no geofence flag (enforcement off)
Check-in is approved by the manager (Check In Approval Setting = Manager Approval). The check-in approval queue does not show an out-of-geofence flag because geofencing enforcement is off for this tenant (Enable geofencing at location / work-area level = No; selfie capture = No). Geofence sites remain configurable on the Geofencing screen, but check-ins are not geofence-flagged — the check-in queue shows Employee, Date·time, Location and Action only. This closes the previously-deferred stale-flag finding.
