This FS adds the build layer — widget data-binding, refresh/cache, drill-down, per-role composition, the aggregation API, and per-screen RBAC projection — on top of the widget inventory fixed in BRD §10.2. It does not restate the widget inventory, the caching policy, the permission matrix, or the visual design; each is referenced to its single source.

2. Screen Specifications
2.1 Dashboard shell (dashboard)
Purpose: the authenticated landing page; assembles a role-composed widget set within the active workspace (Me / My Team / Admin). Satisfies BRD §10.2 (role-aware widgets) and §3.4 (workspace landing).
Layout regions (zones only — visual design per UI Spec v1.0): (a) greeting/status bar — salutation, pending-task count, primary status chips (e.g., Clock-In state, days-to-next-event); (b) primary column — action-oriented widgets (My tasks, Clock-In, Time-off); (c) secondary column — informational widgets (Profile completeness, Company feed); (d) team band (My Team workspace only) — team widgets.
States (reference Foundation Global UI State Standard): loading — per-widget skeletons, shell renders immediately; empty — per-widget empty copy (see catalogue); error — a failed widget shows an inline retry without failing the shell (partial-data is the norm); no-permission — a widget the role cannot see is omitted from the manifest (never rendered-then-blocked).
Composition rule: the shell requests a widget manifest for {role holdings × active workspace × has-reportees} (see §4 GET /dashboard); it does not hard-code widgets.

3. Interaction & Navigation Flows
Workspace switch. The Me / My Team / Admin switcher (Platform §P02/§P03) re-requests the manifest; Admin is an exclusive workspace (OPEN-FS-FND-05, resolved). "My Team" is offered only when has-reportees is true (derived — see §7 / OPEN-FS-CFG-08).
Drill-down. Every widget routes to its owning module screen (catalogue "drill-down" column); the dashboard never duplicates the module screen, it links to it.
Refresh. Widgets refresh on the cadence in §2.2 (applying BRD §10.4); a cache-warm job (Foundation §4, new id JOB-DSH-CACHE) pre-computes heavy team/org aggregations off the request path. Task/approval counts are event-invalidated on the underlying P01 transaction.
No state machine is redrawn — drill-downs hand off to the owning module&#39;s flows (reference each module FS §3).

4. API Contracts
GET /api/v1/dashboard (inventory: BRD §10.2 — role-composed manifest)
Returns the widget manifest for the caller&#39;s {role holdings × workspace × has-reportees}; no widget data, just the composition.
Request: workspace (enum: ME | MY_TEAM | ADMIN, default ME).
Response 2xx: { workspace, widgets: [ { widget_id, region, refresh_ttl_s, drilldown_route } ] }
Errors: 401 (unauth) · 403 (workspace not held by role — reference RBAC) · 422 (invalid workspace).
Auth / pagination / idempotency: reference Foundation FS conventions. Manifest is cacheable per role for the TTL of the shortest-lived widget.
GET /api/v1/dashboard/widgets/{widget_id} (widget data)
Request: path widget_id; optional scope honoured server-side from RBAC (caller cannot widen scope).
Response 2xx: { widget_id, generated_at, ttl_s, payload } (payload shape per widget).
Errors: 403 (widget not in caller&#39;s manifest — reference RBAC §3.7) · 404 (unknown widget) · 503 (source degraded → client shows inline retry, shell unaffected).
Caching: server applies the BRD §10.4 TTL; response carries Cache-Control/generated_at. Reads are scope-enforced server-side (reporting chain / department / entity) — never trust a client scope hint.
POST /api/v1/dashboard/layout (personalisation — optional)
Persists per-user widget order/visibility within the role-permitted set. Tenant-wide layout management is an Analytics Admin capability (BRD §3.6 role; action dashboard.layout.manage — see §7 RBAC registration).
Errors: 403 (widget not in permitted set) · 422 (unknown widget id).

5. Validation
No new field-input validation — dashboard widgets are read-only aggregations. Reference Foundation FS shared catalogue for any drill-down form. The only authored rule is scope integrity: a widget request resolving to a scope wider than the caller&#39;s RBAC data-level grant returns 403 (not a filtered result) — see §4 and §6.

6. Per-Screen RBAC Projection & Menu
Menu entitlement. The single menu entry Home / Dashboard (Foundation FS — Menu & Navigation Entitlement) is visible to all roles; the behind-the-entry composition is the per-persona set in §2.3. No new menu node.
Per-widget visibility projects BRD §3.7 (and §10.2 role-awareness); see the "Visible to" column in §2.2. New content is the projection, not the matrix.
Data-level scope (projects BRD §3.7 row-level security): team widgets resolve to reporting chain for L1–L5; department for HOD; entity/org for CEO/leadership (deferred); self-only for the Me set. Scope is enforced in the API (§4), not the UI.
New action to register in RBAC: dashboard.layout.manage (Analytics Admin) for tenant-wide layout management — see §7.
